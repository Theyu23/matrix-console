# 矩阵账号控制台

Windows 桌面端的本地多账号运营控制台。为每个账号建立独立的会话分区、出口代理和设备画像，做直播聊天采集、评论发布、环境自检与出口实测。

单机运行，无服务端，无遥测，账号数据只存在本机。

## 它解决什么

同一台电脑上登录多个抖音 / 视频号账号，平台会把这些账号关联到一起。关联来自三个层面，本项目针对每一层做一件事：

**会话隔离** —— 每个账号一个 `persist:acct-<id>` 分区，Cookie、localStorage、IndexedDB 天然分开。

**出口隔离** —— 每个账号可以配一条自己的代理，落在分区上，该账号的所有请求（含子资源、媒体流）都从这条出口走。带认证的代理走 `app.on('login')` 回复凭据。

**环境自洽** —— 每个账号的 UA、平台、核心数、内存、语言、时区、WebGL 厂商/渲染器固定成一份画像，按账号 id 播种，长期不变。

第三层有个反直觉的地方：**不是让每台设备长得不一样更好，而是让每台设备长期保持一致**。真实用户的指纹半年不变；一个账号今天报 Windows、明天报 macOS，那才是显眼的特征。所以画像生成一次、存进 localStorage，之后每次都用同一份。

## 核对而不是相信

配了代理不等于流量真的走了代理：地址填错、密码过期、规则没落到分区上，界面上那个「独立出口 N」照样显示得整整齐齐——它数的是配置条数。

所以控制台有一层实测：从每个账号自己的分区发一个请求出去，看对方看到的公网 IP 到底是什么。判据只有一条：**同一台机器上，两个账号的公网 IP 相同，就是同一个来源**。平台看到的也正是这一条。

实测结论会区分出 `proxy-dead`——配了代理但出口仍是本机 IP。这是最要紧的一种：配置看着正常，实际完全没隔离。

## 功能

直播聊天采集与合并、评论话术填充与发布、多账号分屏监看墙、账号环境自检、出口实测与差异核对、账号清单导出（只导身份信息，不含 Cookie 和登录态）。

## 运行

需要 Node.js ≥ 22.12 与 Windows（画像里的平台标识是 Win32，与 Windows 版 UA 一致）。

```bash
npm install
npm run build      # 渲染层构建到 dist/
npm run app        # 启动应用
```

开发时用 `npm run dev` 起 vite 的 watch 构建，`npm run app` 另开一个终端。

渲染层改完必须 `npm run build` 才生效——应用加载的是 `dist/index.html`，不是源码。

## 测试

```bash
npm test
```

纯 `node --test`，不依赖浏览器。覆盖画像与人设自洽性、代理解析与凭据路由、出口实测判定、聊天观察器选择器、崩溃重试、布局计算、打包清单完整性，以及若干条来自真实故障的静态回归（例如主进程 import 的共享模块必须在 asar 清单里、webview 读 URL 必须走容错封装）。

## 打包

```bash
npm run dist       # 生成 release/Matrix-Console-Portable-0.1.0.exe
```

`npm run dist` 会顺带把成品同步到根目录的启动器 exe。

## 已知边界

这几条是方案本身的限制，不是待修的 bug：

**屏幕尺寸和 DPR 是窗口级属性**，一个窗口里所有 webview 共用，按账号改不了。同一窗口的账号在这两项上仍然共享。

**TLS / HTTP2 指纹全机共享**。同一个 Electron 二进制就是同一套密码套件顺序和 ALPN 扩展顺序。这条只能靠分机器解决，代码层面无法绕过。

**不做 canvas / WebGL / 音频噪声**。这类噪声每次刷新都变，本身就能被聚类，而且和真实硬件的稳定特征（核心数、显卡驱动）对不上，比不加更糟。能自洽改掉的只有「平台 + UA + 语言 + 时区 + WebGL 厂商/渲染器」这一组。

**字体列表共享**。中等信号，改造代价大，暂未处理。
